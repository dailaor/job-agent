# 岗位情报 RAG 设计与维护规范

本文定义岗位情报库的首批范围、文档准入、切分、检索、反爬边界和扩展契约。这里的社区内容只用于补足 JD 未披露的信息，不是事实真相，也不能绕过硬规则。

## 1. 当前交付边界

已经实现：

- 一篇帖子一个父文档，按决策主题生成子证据块；
- 本地 SQLite 文档、向量、检索运行和岗位—证据关系表；
- 文档准入、脱敏、重复检测、质量分和时效检查；
- 本地 hashing 向量与 BM25 混合检索；
- “人匹配岗位”和“岗位满足人”两路独立证据包；
- 牛客单篇公开讨论页的有界读取；
- 小红书登录后可见正文的人工导入流程，明确拒绝直接爬取；
- Web、API 和 CLI 管理入口；
- `EvidenceProvider`、`EmbeddingProvider`、`ScoringPort` 和来源注册表扩展点。
- 正职 `full_time` 与实习 `internship` 的独立准入、切片、存储和检索作用域；
- `deepseek-v4-flash` 双维度 Judge、JSON 校验、证据引用校验和规则回退。

仍需持续校准：

- `RuleScoringPort` 继续作为不使用社区证据的可复现基线；
- DeepSeek Judge 只有在 `scoring.provider=deepseek` 且进程环境存在 `DEEPSEEK_API_KEY` 时启用；
- 当前内置 hashing 向量是零依赖检索基线，不等同于语义 embedding 模型；
- 不自动搜索、批量抓取、登录平台或接收 Cookie、Token、密码。

这样拆分可以先稳定语料质量、证据结构和审计链，再接模型，避免把采集噪声直接放大成模型结论。

## 2. 首批公司和岗位族

### 2.1 公司

首批固定为：腾讯、阿里、美团、快手、百度。

选择理由：

1. 五家公司业务线多，同名岗位的真实职责、强度与成长路径差异明显；
2. 产品、数据、算法和后端岗位均有较多社区经验，便于比较不同岗位族的 RAG 增益；
3. 有限白名单便于控制公司别名、正职/实习语境、时效和错误归因。

公司名单是可配置白名单，不代表求职推荐或公司质量排序。

### 2.2 岗位族

| 岗位族 | 纳入方向 | 主要补足的信息 |
|---|---|---|
| `product` | 产品经理、AI/大模型/智能体产品、数据/策略/增长/平台/B 端/用户产品 | 真实职责、决策权、数据要求、跨团队方式、业务线差异 |
| `data` | 数据分析、商业/经营/策略分析、数据科学 | SQL/Python 深度、分析与取数比例、业务影响、汇报对象 |
| `algorithm` | 算法、大模型/LLM/NLP、推荐、搜索 | 技术栈、研究与工程比例、面试深度、算力和业务场景 |
| `backend` | 后端、服务端、Java、Go | 作为技术岗位对照组，验证 RAG 是否真正优于结构较明确的 JD |

当前首轮种子集已经达到每家公司 10 篇：5 篇正职、5 篇实习，共 50 篇。实际来源为牛客 45 篇、小红书 5 篇；岗位族分布为后端 32、算法 11、产品 6、数据 1。它适合验证后端/算法链路和用工类型隔离，不足以声称产品、数据岗位已获得同等质量提升。

下一轮应优先补齐产品与数据岗，并把“公司 × 岗位族 × 用工类型”逐步扩到至少 6 篇有效帖子。理想的公司内岗位分配可先以产品 4 篇、数据 2 篇、算法 2 篇、后端 2 篇为采集目标，同时满足：

- 至少两个独立来源；
- 至少两个能力类主题和三个需求类主题；
- 尽量覆盖两个不同业务线或团队；
- 涉及强度、薪酬、稳定性等敏感结论时，不用单篇帖子下结论。

50 篇种子集只用于验证链路和建立第一版黄金集，不代表已经达到稳定统计结论。后续每个“公司 × 岗位族 × 用工类型”应逐步扩到至少 6 篇有效帖子；不足时必须返回“证据不足”。

## 3. 什么文档值得进入向量库

帖子需要同时满足以下硬条件：

1. **可追溯**：有 HTTPS 原帖链接，声明的平台与域名一致；
2. **范围明确**：能对齐首批公司、一个岗位族，并唯一确认 `full_time` 或 `internship`；
3. **能改变决策**：至少包含一个职责、技能、面试、强度、薪酬、文化、成长、稳定性或办公方式事实；
4. **正文充分**：默认 120–20,000 字，不是标题、列表壳、登录提示或验证码页；
5. **仍有时效**：默认两年内；组织、HC、薪酬和强度应优先近期帖子；
6. **采集方式合规**：小红书只接受人工粘贴或用户登录后当前可见内容；牛客接受人工导入、浏览器可见导入或单篇公开 HTML；
7. **不是主要用于引流**：软广、课程、付费咨询、内推码和联系方式占主导时拒绝；
8. **一帖一文档**：不把多篇帖子、评论区和二手总结拼成一个来源不清的文本。

准入状态：

| 状态 | 行为 |
|---|---|
| `accepted` | 脱敏、切块、生成向量，可以检索 |
| `needs_review` | 保存来源和原因，不生成向量；当前主要用于发布时间缺失或格式不明 |
| `rejected` | 保存拒绝原因，不生成向量 |
| `duplicate` | 保存跨平台来源关系，不重复生成向量 |

质量分只用于同一检索范围内的排序，不把主观帖子变成“高质量事实”。当前加分项包括正文信息量、主题覆盖、业务线、可解析发布时间和亲历语义；硬性失败时质量分归零。

默认 `retain_full_text=false`：不保存整篇原文，只保存脱敏后的决策证据块、内容哈希、作者哈希和必要来源元数据。手机号、邮箱和单行微信号会在向量化前替换。

## 4. 切分策略

### 4.1 父文档粒度

一篇帖子是一份父文档，父文档保存：

- 平台、原帖 URL、标题和发布时间；
- 规范公司、岗位族、用工类型、业务线、城市和年资；
- 采集方式、准入结果、原因、主题和质量分；
- 内容哈希、作者哈希和重复来源关系。

不建议把整篇帖子只做一个向量。长帖通常同时包含面经、职责、加班和氛围；整帖向量会稀释查询意图，并把与当前决策无关的叙事一起塞给模型。

### 4.2 子块粒度

子块以“一个能独立影响决策的主题”为边界：

- 能力侧：`duties`、`skills`、`interview`；
- 需求侧：`workload`、`compensation`、`culture`、`growth`、`stability`、`work_style`。

实现规则：

1. 先按中文句号、问号、感叹号、分号和换行切句；
2. 超过 320 字的长句再按逗号、顿号或冒号拆分；
3. 相邻同主题句合并，目标 50–320 字；
4. 不做机械重叠，避免同一观点在 Top-K 中重复占位；
5. 无决策主题的寒暄和叙事不单独入向量；紧随主题的解释可并入当前主题；
6. 每个子块保留父文档 ID、原文偏移和块哈希；
7. 向量文本前加入上下文前缀：公司、岗位族、用工类型、来源、主题，以及已知业务线、城市、级别和发布时间。

示例：

```text
[公司=腾讯｜岗位族=product｜用工类型=full_time｜来源=nowcoder｜主题=interview｜业务线=腾讯云｜发布时间=...]
二面重点追问 SQL、实验设计和大模型评测方法……
```

这套策略兼顾“一篇帖子是一个完整证据来源”和“每次检索只取与决策相关的原子事实”。

## 5. 检索与评分边界

固定顺序：

```text
岗位真实性校验
  → 硬规则过滤
  → 规范公司、岗位族与用工类型
  → 两路混合检索
  → EvidenceBundle
  → RuleScorer 或未来 LlmScorer
  → 双向分数与解释
```

任何学历、地点、薪资、时效或黑名单硬规则失败时，不运行社区证据检索。帖子不能“救回”硬条件不满足的岗位。

需求侧还必须与用户明确填写的软偏好比较：工作强度取向、职责边界取向、成长/稳定性优先级、希望的团队文化和希望避开的体验风险。用户没有表达取向时，Judge 不得自行假设“高强度一定差”或“成长机会一定好”；这类帖子只能降低不确定性，不能替用户定义偏好。

### 5.1 两路检索

- **人匹配岗位**：检索职责、技能和面试。允许同岗位族跨公司补足通用能力要求，但必须与岗位用工类型完全一致。
- **岗位满足人**：检索强度、薪酬、文化、成长、稳定性和办公方式。必须同公司、同岗位族、同用工类型。

正职与实习之间没有降级或回退路径。岗位明确为实习时只检索实习；普通岗位未给出类型且没有实习信号时标记为 `regular_job_default/full_time`，并把推断来源写入 coverage。

默认每路最多 6 个块、同一父文档最多 2 个块。排序为：

```text
48% hashing 向量相似度
+ 27% BM25 词法相关度
+ 10% 文档质量
+ 10% 时间衰减
+  5% 公司精确匹配
```

hashing 向量使基础包零额外模型依赖，BM25 保证 SQL、业务线和岗位关键词仍能精确命中。替换为真实 embedding 时应给 provider 使用版本化名称，重新索引后再切换，不能把不同维度或模型的向量混用。

### 5.2 证据覆盖与置信度

- 4 篇以上且至少两个来源：`high`；
- 2 篇以上：`medium`；
- 1 篇：`low`；
- 无文档：`insufficient`。

这是检索覆盖度，不是事实置信度或模型正确率。最终解释必须显示原帖标题、链接、发布时间、主题和检索分，允许用户回查。

## 6. 小红书和牛客的采集边界

平台规则和页面结构可能变化，现场使用前要重新核对。当前安全策略如下。

### 小红书

- 不提供直接 HTTP 爬虫；
- 只允许在用户已登录浏览器内做有界人工选材；每次一个聚焦查询、逐篇检查，不自动翻页、不并发打开和不绕过访问限制；
- 不接收或复用 Cookie、Token、密码；
- 用户自行登录后，只导入当前页面实际可见的单篇正文；
- 若直接把链接交给读取接口，只返回 `auth_required` 和人工导入说明；
- 登录提示、验证码、访问频繁和加载壳一律拒绝入库。

### 牛客

- 只读取用户明确提供的 `https://*.nowcoder.com/discuss/<id>` 单篇公开讨论页；
- 不调用社区搜索、列表、分页、登录接口或私有 API；
- 请求使用透明 User-Agent，最短间隔 5 秒、超时 15 秒、响应上限 2 MB；
- 不自动重试；HTTP 403/429、验证码或访问限制立即停止；
- 只解析公开 HTML 中可验证的帖子状态，入口页和 SSR 加载壳不入库。

平台内容应仅在用户有权使用的场景下做本地个人分析，保留原始链接并支持删除。涉及转载、共享语料或商业使用时，需要另行处理授权与版权，不能因为内容能访问就默认可以再分发。

## 7. 存储与集成

知识表与原有岗位、评估和投递表分离：

- `knowledge_documents`：父文档与准入元数据；
- `knowledge_chunks`：主题块、上下文文本和 float32 向量；
- `knowledge_retrieval_runs`：每次岗位检索查询与完整证据包；
- `evaluation_evidence`：岗位、证据块、维度、排名和分数关系。

原有 `jobs`、`evaluations` 和 `applications` schema 不需要迁移。`JobAgent.evaluate()` 在硬规则通过后调用可选 `EvidenceProvider`，再把 `EvidenceBundle` 交给 `ScoringPort`；没有知识库、检索失败或未来模型失败时，规则链仍可独立运行。

主要入口：

```text
Web:  岗位情报库页面
API:  /api/knowledge/status
      /api/knowledge/documents
      /api/knowledge/fetch
      /api/knowledge/retrieve
      /api/knowledge/jobs/<job_id>/evidence
CLI:  knowledge-import / knowledge-fetch / knowledge-list / knowledge-retrieve
```

## 8. 扩展方式

### 增加公司或岗位族

只修改 `knowledge.company_aliases` 或 `knowledge.role_families`，并增加别名识别与检索 fixture；不要在 policy、retriever 或编排器里写公司 ID 分支。

### 增加来源

实现 `KnowledgeSource.fetch(url) -> SourceFetchResult` 并注册到 `SourceRegistry`。新来源必须先定义允许域名、公开/登录边界、限速、超时、响应上限和失败状态，再写解析器。

### 替换 embedding

实现 `EmbeddingProvider` 的 `name`、`dimensions` 和 `embed(texts)`，通过 `KnowledgeService(..., embedding_provider=...)` 注入。模型名必须版本化；切换 provider 需要重建全部块向量。

### DeepSeek Judge

`DeepSeekScoringPort.score(job, config, evidence)`：

- 结构化输出两个独立 0–100 分、置信度和逐条引用；
- 明确区分 JD 事实、用户档案事实和社区经历；
- 多来源冲突时输出冲突，不做无证据裁决；
- 证据不足时降低置信度，不补写事实；
- 解析失败或超时回退 `RuleScoringPort`；
- 任何情况下都不能改写硬规则结论。
- API Key 只从 `scoring.api_key_env` 指向的进程环境变量读取，不进入 JSON 配置、日志或评测报告。
- `preferences` 中的岗位体验字段随任务配置进入 Judge；姓名、联系方式和完整简历文件不会发送。

批量入口：

```powershell
$env:PYTHONPATH='src'
.\.venv\Scripts\python.exe scripts\import_knowledge_corpus.py --file <corpus.json> --require-quota --dry-run
.\.venv\Scripts\python.exe scripts\evaluate_judge.py --benchmark <gold.json> --provider both --order-check --output <report.json>
```

## 9. 评测门禁

在让 RAG 影响最终分数前，建立人工黄金集并至少验证：

| 指标 | 目的 |
|---|---|
| 准入精确率 | 被向量化的文本是否真的含岗位决策事实 |
| 公司/岗位族归因准确率 | 是否把帖子对齐到正确作用域 |
| 主题块纯度 | 一个块是否只表达一个主要决策主题 |
| Recall@6 / nDCG@6 | 人工相关证据能否进入前六名且排序合理 |
| 来源与父文档多样性 | Top-K 是否被同一帖子或同一平台垄断 |
| 引用正确率 | 模型理由是否能逐条回到真实证据块 |
| 硬规则守恒 | 加入任何社区文本后，硬拒绝结果都不得翻转 |
| 决策增益 | 相比只看 JD，双向判断是否更接近人工复核结果 |
| 正职/实习泄漏率 | 任何检索和引用都不能跨 `employment_type`，目标为 0 |
| JSON 有效率 | 模型输出通过结构、枚举、区间和必填字段校验的比例 |
| 证据引用正确率 | 引用块必须存在、属于正确维度并满足作用域 |
| 顺序稳定性 | 反转证据顺序后策略/关系应一致，分数变化应受控 |

每次修改准入、切块、embedding、权重或提示词，都要固定黄金集做对比；真实站点页面只做小规模现场冒烟，不作为长期稳定 fixture。

当前初始黄金集位于 `tests/fixtures/rag_judge_benchmark.json`，包含五家公司各一组正职/实习用例。它在模型运行前预先制定，但仍标记为 `provisional_needs_human_adjudication`；生产门禁前需要两名独立复核者和分歧仲裁。主要因果对照是同一个 `deepseek-v4-flash` 在 `no_rag` 与 `rag` 两种证据条件下的配对结果；规则评分只是离线可复现的次级基线。报告同时给出策略、能力关系、需求分数区间、JSON 有效率、能力/需求引用合规、用工类型泄漏和证据顺序稳定性。
